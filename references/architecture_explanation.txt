 Here is the complete, deep-dive explanation of this architecture.

  To understand this system, you need to understand that it has two completely separate lifecycles:

  1. The Offline Ingestion Pipeline: Runs once beforehand to sanitize the PDFs, extract tables, and build local search indexes on the hard drive.
  2. The Online Query Pipeline: Runs in real-time when an analyst types a question into the browser.

  ### Phase 1: The Offline Ingestion & Defense Pipeline

  (Runs as a CLI command before the web app starts: python -m src.ingest.build_index)

    [PDF Corpus] ──> [Sanitizer] ──> [Table Parser] ──> [ONNX Embedder] ──> [Local Storage]

  #### 1. PDF Corpus (/data/pdfs)

  • What it is: The folder holding all the SEC 10-K filings (from FinanceBench) plus the 3 poisoned PDFs containing planted attacks (white text,
  microscopic font, and malicious prompt injections).

  #### 2. Sanitizer (PyMuPDF Span Filter) — Defense Layer 1

  • Why it exists: Attackers hide prompt injections inside PDFs using visual tricks that humans can't see but standard AI extractors blindly read.
  • What it does: It opens every PDF page and inspects the raw visual coordinates:
      • Drops microscopic fonts: Anything with a font size smaller than 4.5pt is thrown in the trash.
      • Drops invisible/white text: If the text color matches the background (e.g., #FFFFFF white text on a white page) or uses invisible render modes
      (Tr=3), it is deleted.
      • Drops off-canvas text: If text coordinates are positioned outside the page boundary (e.g., negative coordinates), it is dropped.
      • Purges metadata: Strips author info, embedded scripts, and PDF annotations.


  #### 3. Table Parser (Docling + Header Propagator)

  • Why it exists: In financial reports, tables like "Consolidated Statements of Operations" are multi-column and often split across pages. Standard RAG
  slices text into 500-character chunks, which rips numbers away from their column headers (FY2023 vs FY2022) and units ($ in millions).
  • What it does:
      • Uses Docling to convert tables into clean GitHub-Flavored Markdown tables.
      • Header Propagator: If a table continues onto page 59 from page 58 without repeating headers, our parser detects (Continued) and automatically
      prepends the column years and unit scales to page 59.
      • Page-Bounded Invariant: A chunk never crosses a physical page boundary. This ensures that every chunk strictly maps to one physical PDF page
      (#page=N).


  #### 4. ONNX Embedder (bge-small-en-v1.5 INT8)

  • Converts the clean text chunks into 384-dimensional mathematical vectors.
  • Runs in INT8 ONNX format, which cuts model RAM usage down to just 130 MB (instead of 800 MB+ in standard PyTorch).

  #### 5. Local Persistent Storage (Hybrid Index Store)

  • Saves three lightweight files directly to the local SSD:
      1. chunks.sqlite: Text, document IDs, physical page numbers, and table flags (≈ 28 MB).
      2. faiss.index: Dense vector search index (≈ 35 MB).
      3. bm25.pkl: Inverted keyword dictionary (≈ 45 MB).
  • Crucial Engineering Decision: Once this pipeline finishes, the heavy parsing libraries (Docling, PyMuPDF) are completely unloaded from RAM. Total
  memory released: 100%.

  ### Phase 2: The Online Serving Pipeline

  (Runs in real-time when the analyst uses the web app)

  #### 1. Edge Layer (Caddy Reverse Proxy + Web UI)

  • Caddy: Serves as the web gatekeeper on Ports 80/443. It forwards API calls to FastAPI and serves raw PDF files using HTTP range requests.
  • Web UI: A clean, split-screen interface:
      • Left Side: A single search box where the analyst types their question, plus the final answer, calculated metrics, and clickable citation badges.
      • Right Side: A PDF.js viewer. When you click a citation badge (e.g., [AMZN_2023_10K.pdf | Page 58]), the PDF viewer automatically jumps directly
      to #page=58 and highlights the quote.


  #### 2. Query Router (Query Parser & Entity Filter)

  • When the analyst hits submit, this component checks the question in 15 milliseconds without using any LLM:
      • Extracts company tickers (AAPL, AMZN, TSLA) and fiscal years (2022, 2023).
      • Quick Abstention Check: If the user asks about "Nike FY2023" and our folder only contains Amazon and Apple, the router stops immediately and
      returns "Not in the documents". Cost: 0 tokens, 15ms latency.


  #### 3. Hybrid Retriever (BM25 + FAISS via Reciprocal Rank Fusion (RRF))

  • If the company exists, it runs dual retrieval:
      • BM25 finds the Top-30 exact keyword matches (great for exact line items like "Operating Lease Liabilities" or "Item 1A").
      • FAISS finds the Top-30 conceptual semantic matches (great for concepts like "cash burn" or "supply chain disruptions").
  • RRF (k = 60): Merges both 30-item lists using rank math:

                      1                   1
    Score(c) = ──────────────── + ─────────────────
               60 + rank    (c)   60 + rank     (c)
                        BM25               FAISS

  It boosts tables by 1.15x for numerical queries and selects the Top-12 best overall candidate chunks.

  #### 4. ONNX Reranker (bge-reranker-base INT8)

  • Instead of blindly sending 12 chunks to the LLM (which would blow our token budget), we use a cross-encoder model to score how relevant each chunk is
  to the question.
  • Running on 2 vCPUs in INT8 ONNX, it evaluates all 12 pairs in ~650 ms and narrows them down to the Top-4 highest quality evidence passages.

  #### 5. Abstention Gate (Confidence Gate + XML Nonce Prompt Sandbox)

  • This is a critical two-way fork in the road:
      • Path A (Score < -1.50): If the highest-scoring passage has a confidence logit below -1.50, it means the documents don't have the answer. The
      system halts immediately and outputs "Not in the documents". Total tokens used: 0.
      • Path B (Score ≥ -1.50): Valid evidence exists. The gate wraps the 4 chunks inside randomized, per-request XML nonce tags:
        <untrusted_filing_data_9f8a3c>
        [DOC: AMZN_2023_10K.pdf | PDF_PAGE: 58]
        Net sales were $574,785 million...
        </untrusted_filing_data_9f8a3c>
      This prevents prompt injection: even if the PDF contains the words "Ignore previous instructions", the model knows it is untrusted passive data.


  #### 6. Circuit Breaker (httpx AsyncClient)

  • Wraps the HTTP request to the LLM proxy with strict timeouts:
      • Connect Timeout: 1.2 seconds
      • Read Timeout: 3.2 seconds
      • Client Retries: 0 (do not retry!)
  • What happens during the 60s Outage Test?
  If the evaluator stops the proxy, the connection fails within 1.2s. The circuit breaker trips and instantly returns the Top-4 passages we already found
  locally with clickable #page=N links in 1.95 seconds.

  #### 7. LLM Governance Tier (LiteLLM Proxy + Postgres Audit DB)

  • LiteLLM Proxy: The authorized gateway. It enforces the strict rule of maximum 20 Requests Per Minute (RPM).
  • PostgreSQL 16: Every single request, prompt token, and completion token is logged into the LiteLLM_SpendLogs table so the judges can audit our token
  consumption (≤ 80, 000 stretch goal).
  • Upstream Routing:
      • Primary: Groq (llama-3.3-70b-versatile) — free and ultra-fast.
      • Fallback: If Groq returns an error (429/503), LiteLLM automatically redirects to OpenRouter / Gemini free models.


  #### 8. Math & Citation Verifier (AST Decimal Calc + Substring Page Verifier)

  • When the LLM responds in structured JSON:
      1. Safe Arithmetic (AST Math): If the question asked for a margin or YoY % change, the LLM does not do mental math. It emits the formula string:
      "(36852 / 574785) * 100". Our backend parses this through Python's Abstract Syntax Tree (ast.parse) and computes the exact result using decimal.
      Decimal. Zero hallucinated math, 100% precision.
      2. Page Citation Verification: The verifier takes the LLM's verbatim_quote and checks if that exact sentence actually exists on doc[pdf_page_number
      - 1]. If it matches, the verified answer and clickable badges are sent to the user interface.
